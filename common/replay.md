# 世界录像设计

状态：设计阶段，尚未实现记录器、接口或播放功能。

## 阶段范围

第一版按世界、按 tick 记录全部生物的操作数据，作为以后世界录像的输入轨迹。只记录服务器最终接受的 tick；暂停、旧快照被拒绝、存档失败的尝试不产生录像帧。

目前不记录地形、汤层、生物位置、速度、储能和完整世界快照，也不提供可视化播放。仅有操作数据无法准确还原世界，不能承诺通过重新执行指令复现原来的运动。后续增加世界关键帧、状态变化和生命周期事件后，再提供播放与跳转。

不重复保存 Python 源码、AI 记忆、查询过程、完整日志或 worker 性能指标。现有 `ai.history` 用于近期调试，仍保留其 256 条上限；录像独立保存，不受该上限影响。

## 时间轴

- 为世界增加持久化的 `tick: u64`，表示已经成功提交的模拟 tick 数量。
- 新世界或旧存档缺少该字段时从 0 开始，首个录像帧为 tick 1。
- 每个成功提交的 tick 加一，包含没有生物、没有 AI 或没有指令的 tick。
- 每帧保存 `dt_ms`，当前为 1000，表示该帧从 tick 开始到结束推进的模拟时间。
- 暂停不推进 tick，恢复和服务器重启后续写；慢 AI 不增加额外 tick。
- `committed_at` 保存 UTC 时间，仅供查询和排查，播放时间以后按 `dt_ms` 累计。
- 不使用 `game.time.step` 或 `ai.calls` 作为世界时间；它们是各实例独立的 AI 调用序号。

旧世界从接入记录器时开始记录，无法补录此前的操作。每段录像用独立 `recording_id` 标识，清空或回滚世界存档后必须开启新段，避免同一录像内 tick 重复。

## 每 tick 记录内容

每帧枚举该 tick 开始快照中的全部生物，按实例 UUID 排序；每个生物包含：

| 字段 | 含义 |
| --- | --- |
| `organism_id` | 生物实例 UUID，用于区分同一模型生成的实例 |
| `ai.status` | `success`、`failed`、`skipped` |
| `ai.call` | 本轮实际提交的调用序号；未调用为 null |
| `ai.code_version` | 已有代码内容版本；未获得版本时为 null |
| `ai.skip_reason` | 未调用原因：`no_energy` 或 `ai_disabled`；否则为 null |
| `ai.error` | 失败原因，最多 2048 字符；其他状态为 null |
| `submitted_commands` | 本轮成功 AI 输出中，每个组件最后一条有效指令；失败或未调用为空 |
| `control_source` | `new_output`、`previous_output` 或 `none` |
| `controls` | 该 tick 交给器官执行层的最终控制信号，执行前复制 |

命令复用现有 `ComponentCommand`，保留组件 UUID、方法、物质和原始请求速率。同一组件最后一条有效指令生效，记录按组件 UUID 排序；不逐次记录 Python 中被后续调用覆盖的中间输出。

`controls` 是输入，不表示器官实际完成了相同数量的喷射或吸收。当前执行层会进行档位取整、耐久和能量限制，第一版不记录这些执行结果。后续可增加 `execution_results`，记录实际速率、扣能、物质转移及拒绝原因，与输入分开。

### 控制语义

- AI 成功且输出非空：来源为 `new_output`，采用本轮输出。
- AI 成功且输出为空：来源为 `new_output`，控制为空，表示清除旧控制。
- AI 失败：保留失败状态，采用上次成功控制；有旧控制时来源为 `previous_output`，否则为 `none`。
- AI 未调用：明确记录跳过原因；按执行层现有规则选择控制，旧控制非空时来源为 `previous_output`。
- 无能量或损坏的器官可能有控制输入，但执行量为零，不能据此伪造实际动作。
- 即使控制为空，也必须保留该生物记录；无生物的 tick 写入 `organisms: []`。
- worker 异常或调度任务失败也应形成失败结果，不能把已派发却失败的调用写成未调用。

操作必须在 `dynamics::advance` 之前采集。执行层可能因为能量耗尽清空 `pending_commands`，事后读取会丢失本 tick 原本采用的控制。

## 文件组织

录像保存到配置文件同级的数据目录，与当前世界快照分开：

```text
data/world_replays/<world_id>/<recording_id>/
  manifest.json
  frames/
    00000000000000000001.json
    00000000000000000002.json
```

第一版每个 tick 一个不可变 JSON 文件，以 20 位十进制 tick 命名，便于检查、按范围读取和原子落盘。先写同目录临时文件并同步，再用仓库统一的原子替换策略发布，读取时忽略临时文件。必须处理 Windows 下的文件替换行为。

`manifest.json` 包含格式版本、世界 UUID、录像 UUID、开始时间、首个 tick、引擎版本，以及 `features: ["organism_controls"]`。帧本身是 tick 范围的事实来源，不要求每 tick 改写 manifest 的最后帧字段。

该方案易于实现，但 1 秒一帧会为每个持续运行的世界每天产生 86400 个小文件。规模增大后迁移为分段帧文件和索引，保持帧模型不变。第一版不自动清理，需在实施部署时评估存储容量；暂停和重启不删除录像，删除世界或账号时同步删除其录像。

未配置磁盘数据目录的内存世界不产生持久录像，测试中可注入临时目录，不声称已经保存录像。

## 与世界提交的一致性

记录点设在 `WorldDirectory::commit_tick`。不能在单个 AI worker 返回时写帧，否则会记录后来因暂停或快照过期而被拒绝的操作，也无法覆盖无 AI 的 tick。

世界快照与录像是两个文件，不能依靠简单的写入顺序实现原子提交。第一版使用快照内的单帧待写记录，保证录像失败可恢复：

1. 获取世界运行锁，校验活动状态、快照版本和全部 AI 结果。
2. 若世界有待写帧，先按下述恢复规则写出；完成前不开始新的 tick 提交。
3. 在副本中应用 AI 结果，采集完整操作帧，执行动力学，令 `tick` 加一。
4. 将更新后的世界和 `pending_replay_frame` 一起原子保存到世界快照。该步失败时不发布状态，也不生成最终录像帧。
5. 以 `(recording_id, tick)` 为唯一键写出不可变帧。已有且内容相同视为成功；内容不同报冲突，不覆盖。
6. 帧写出后尝试清除快照中的 `pending_replay_frame` 并保存。清理失败可保留待写字段，下次按相同唯一键重复处理。
7. 一旦第 4 步保存成功，该 tick 就已提交，必须发布相应世界状态。第 5、6 步失败应报告为“已提交，录像待恢复”，不能当作 tick 未提交重新执行 AI、扣能或推进物理。

启动、恢复世界、下次 tick 或暂停保存时处理待写帧。写帧持续失败时暂停该世界的进一步推进并报告错误，不能静默丢帧或无限积压；暂停本身仍可保存已有待写信息。恢复后先重试录像写入，再允许新 tick。

只有一个待写帧，因此内存和快照增长有界。帧文件单独存在而 manifest 缺失时，可根据快照的录像身份修复元数据；世界快照不存在时不得把孤立帧解释成已恢复的运行世界。

## 后续世界录像

沿用录像 UUID 和 tick 时间轴，增加以下数据类型：

- `world_keyframe`：某个 tick 边界的完整世界，包括生物结构、运动、组件状态、地形及物质。
- `world_delta`：该 tick 的状态变化，用于连续播放；定义清楚是 tick 开始还是结束状态。
- `events`：tick 之间的生物创建、删除、死亡、世界设置变化等有序事件。
- `execution_results`：实际执行的器官结果，用于动作展示与调试。

播放以已记录状态为准，不重新运行玩家 Python。第一版操作轨迹会标记为仅支持操作查看，加入状态数据后的录像段再声明可视化播放能力；不假定旧轨迹自动获得播放能力。

## 实现落点与验证

建议新增 `server/src/game/replay.rs` 定义帧模型，独立存储模块负责写帧、恢复、范围读取。`runner` 提供调度结果及跳过原因，`commit_tick` 负责采集和提交。世界存档增加 `tick`、录像身份和可选待写帧，旧字段缺失时兼容默认值。

第一版先完成服务端记录与恢复，不增加播放器页面。后续操作查询接口按世界归属鉴权，使用 tick 范围和固定上限分页，避免一次读取全部录像。查询不得依赖仍然存在的源模型，也不得泄露其他用户的世界录像。

实现时验证：成功输出、空输出清除、失败沿用旧控制、无能量与 AI 关闭、空世界、多生物排序、AI 返回顺序无关、能量耗尽后的输入保留、暂停和过期快照不写帧、重启续号、世界保存失败、帧写入失败恢复、清理失败幂等、冲突帧拒绝覆盖、损坏 JSON 报错，以及删除世界时清理录像。
